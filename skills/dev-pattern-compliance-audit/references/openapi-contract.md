# OpenAPI / Swagger as API contract

OpenAPI 3.x (and Swagger 2) documents are the process-boundary contract for HTTP APIs. In PEAA terms they
encode **Data Transfer Object** shapes and the **Remote Facade** surface (operations, status codes, errors).
In GoF terms, generated clients are often **Gateway + Proxy**; generated models are **DTO / Value-like**
transfer types — not domain entities.

Apply the same fit test as the rest of the skill: only report when force and evidence are real.

---

## 1. Locate the contract

| Signal | Meaning |
|--------|---------|
| Committed `openapi.yaml` / `openapi.yml` / `openapi.json` / `swagger.yaml` | Likely **contract-first** |
| Springdoc / springfox, Nest `@nestjs/swagger`, FastAPI auto-schema, tsoa | Likely **code-first** (spec derived from code) |
| `openapitools.json`, `orval.config.*`, `openapi-ts.config.*`, `speakeasy.yaml`, `fern/` | Codegen is intentional |
| Both a hand-edited spec *and* annotation export with no single publish step | Dual source of truth — finding |

Also check CI jobs and package scripts (`generate:api`, `openapi-generator-cli`, `openapi-typescript`, …).

---

## 2. Contract-first vs code-first

| Style | Healthy shape | Failure modes |
|-------|---------------|---------------|
| **Contract-first** | Spec is reviewed/merged; server stubs and/or clients generated; CI fails on drift | Spec ignored at runtime; generated code edited by hand; second hand-written client |
| **Code-first** | Annotations/decorators are the design surface; exported OpenAPI is published for consumers | Exported spec not published; consumers reverse-engineer routes; annotations drift from behaviour |

Neither style is mandatory. Report only inconsistencies and coupling pain.

---

## 3. Code generation — what to credit

These are the *correct* implementations of DTO / Gateway when present — do **not** recommend hand-rolling instead:

| Tool / artifact | Pattern role |
|-----------------|--------------|
| openapi-generator / OpenAPI Generator CLI | Server stubs, client SDKs, models (DTO) |
| openapi-typescript / openapi-fetch | TS types + fetch client (DTO + Gateway) |
| orval | React Query / fetch clients + models |
| speakeasy, Fern, Kiota, Stainless | Multi-language SDKs (Gateway) |
| Spring `openapi-generator` maven/gradle plugin | Java/Kotlin models + API interfaces |
| `@hey-api/openapi-ts`, kubb, oazapfts | TS client variants |

**Markers in generated files** (do not "fix" these; treat as owned by the generator):

- `// Code generated by … DO NOT EDIT`
- `@Generated`, `/* tslint:disable */`, `eslint-disable`
- Paths under `generated/`, `api/generated/`, `src/gen/`, `packages/*-client/`

**Finding when:** a parallel hand-written client or DTO package duplicates the generated one without a documented reason (Migration, experimental field, etc.).

## 3b. Frontend generation axiom (v1.3)

**Axiom:** When a published OpenAPI document exists for an HTTP API *and* the same repo (or a clearly coupled
frontend package) contains a TypeScript/JavaScript browser app, SPA, Next.js/Remix app, or BFF that calls that
API, the **default correct Gateway** is a **client generated from the OpenAPI spec** — not a growing hand-written
`api/` module of axios/fetch helpers and manually typed DTOs.

### Preferred toolchain (pick one; consistency > brand)

| Tool | Typical output | Fits well with |
|------|----------------|----------------|
| **orval** | Typed fetch/axios clients + optional React Query hooks | React / Next |
| **openapi-typescript** + **openapi-fetch** | `paths` types + thin typed client | Any TS frontend |
| **kubb** / **@hey-api/openapi-ts** / **oazapfts** | Clients + optional hooks | React / general TS |
| **openapi-generator** `typescript-fetch` / `typescript-axios` | Classic SDK-style client | Monorepos already on generator CLI |

### Healthy shape

1. Spec path is stable (`openapi/openapi.yaml` or URL to published artifact).
2. `package.json` (or monorepo task) has `generate:api` / `openapi` script.
3. CI runs generation and fails on dirty tree (or commits generated output deliberately).
4. App code imports only from the generated package/path (e.g. `src/api/generated`, `@acme/api-client`).
5. Thin adapters allowed *above* the generated client (auth header injection, base URL, error toast mapping) —
   those are Decorators around the Gateway, not a second client.

### Findings (with force)

| Situation | Verdict | Typical severity |
|-----------|---------|------------------|
| OpenAPI + TS frontend, only hand-rolled `fetch`/axios API module | Missing generated Gateway | Medium |
| Generated client exists but features still call parallel hand-rolled helpers for the same paths | Dual Gateway / drift | Medium–High |
| Generated files edited by hand (no DO NOT EDIT respect) | Misapplied codegen | Medium |
| Spec changes with no generate step in CI/scripts | Process gap | Medium |
| Hand-rolled client for *one* experimental endpoint during migration, documented | OK — trade-off | — |

### Exceptions (do not report as defects)

- Frontend is not TypeScript/JavaScript, or no mature generator is available for the stack.
- Prototype / spike with ≤2 endpoints and no second consumer.
- Generated client for a *different* API; this app only talks to an internal non-OpenAPI service.
- GraphQL-first frontends using GraphQL Code Generator instead (different contract).

### Recommendation shape

Smallest step: add `orval.config.ts` (or equivalent) pointing at the existing spec → `npm run generate:api` →
replace one feature’s hand-rolled calls → enforce in CI. Do not demand a rewrite of the entire frontend in one change.

## 4. Fidelity checks (evidence-based)

Sample; do not exhaust every path on a large API.

1. **Path coverage** — pick 5–10 important operations from the spec; confirm matching controller/route handlers exist (and vice versa for public controllers).
2. **Schema vs payload** — for one write and one read operation, compare required fields / enums / nullability between OpenAPI schema and the type actually bound in the handler or returned.
3. **Status codes** — documented error responses (4xx/5xx) vs what the code actually returns (`@ResponseStatus`, exception handlers, Nest filters).
4. **Auth** — `securitySchemes` vs real middleware/filters; public routes accidentally behind auth or the reverse.
5. **Versioning** — `info.version`, URL prefix (`/v1`), or header version vs deployment reality.
6. **Frontend client usage** — if a generated client exists, grep for raw `fetch(` / `axios.` to the same API
   base path outside the generated module; those are dual-Gateway leads.

Severity:

- **High** — breaking mismatch in production (wrong required field, silent data drop, auth gap).
- **Medium** — drift that will break the next consumer or codegen refresh.
- **Low** — cosmetic description/example drift.

---

## 5. Process boundary rules

| Practice | Verdict |
|----------|---------|
| OpenAPI schemas map to dedicated API models / generated DTOs | Well applied |
| JPA/Prisma entities (or domain aggregates) exposed as OpenAPI schemas | Misapplied / coupling — Medium or High if clients break on schema renames |
| Hand-rolled `fetch` + inline types while orval/openapi-typescript client exists | Over-engineered duplicate or Missing use of Gateway |
| OpenAPI + TS SPA with no generated client and a growing hand-rolled `api/` layer | Missing frontend generation axiom (Medium) |
| Spec committed but never used to generate or validate | Missing force for contract-first (or dead artifact) |
| Multiple services copy-paste the same YAML without a shared package | Shotgun surgery on the Remote Facade |

---

## 6. What not to report

- Absence of OpenAPI on a private library, CLI, or single-service internal RPC with one client and no public HTTP surface.
- Preferring code-first over contract-first (or the reverse) when the chosen style is consistent and documented.
- Generated code style (verbose names, extra interfaces) — that is generator configuration, not a pattern defect.
- GraphQL-only or gRPC-only APIs unless an OpenAPI gateway is also claimed.

---

## 7. Report wording

- Architecture profile: one row or short subsection — **API contract**: contract-first | code-first | none; tool; path to spec; **FE client**: generated (orval/…) | hand-rolled | n/a.
- Findings: title the problem ("Order create response missing fields required by openapi.yaml — DTO drift"; "SPA uses hand-rolled axios while openapi.yaml exists — missing generated Gateway"), not "use OpenAPI".
- Recommendations: smallest step (add orval/openapi-typescript script; regenerate client; replace one feature path; add CI dirty-check; spectral/openapi-diff; stop exporting entities; publish one spec artifact).
